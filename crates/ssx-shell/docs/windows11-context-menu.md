# Windows 11 top-level context menu: design

Status: **design only**. Nothing here is built or tested on Windows yet. What exists today:

* `ssx_shell::windows::manifest::sparse_package_manifest` generates the `AppxManifest.xml`
  described below (golden-tested and checked for well-formedness in
  `tests/golden/windows/AppxManifest.xml`).
* `ssx_shell::windows::manifest::clsid_for` gives the stable CLSID of each action's command.
* The classic registry verbs (`ClassicVerbs`) and Send To (`SendTo`) work on Windows 10 and 11
  and are the fallback until this is implemented.

## Why a second mechanism

Windows 11's redesigned context menu shows only entries from *packaged* extensions
(`IExplorerCommand` registered through a package manifest). Classic `HKCU\...\shell\...` verbs
are still honoured but are hidden behind **Show more options** (Shift+F10). ssx wants
"Upload with ssx" at the top level, so it needs:

1. a small COM DLL implementing [`IExplorerCommand`][iec] (one class per menu entry);
2. package identity for the otherwise unpackaged ssx, via a **sparse package**;
3. a signature on that package.

[iec]: https://learn.microsoft.com/windows/win32/api/shobjidl_core/nn-shobjidl_core-iexplorercommand

## Components

```
Explorer.exe ── right-click ──▶ shell reads package manifest
                                   │  desktop4:FileExplorerContextMenus
                                   ▼
                        dllhost.exe (COM surrogate, out of process)
                           └─ ssx_shell_ext.dll   IExplorerCommand::Invoke(IShellItemArray)
                                   │  one message with ALL paths
                                   ▼   ssx-ipc client (named pipe, owner-only ACL)
                              ssx.exe (running app)  ── or spawned if not running
```

* **`ssx_shell_ext.dll`** (future crate `ssx-shell-ext`, `crate-type = ["cdylib"]`, built with
  the `windows` crate's `#[implement]`). Exports `DllGetClassObject` and `DllCanUnloadNow`.
  Contains no upload logic. Keep it tiny so a bug cannot hurt anything but the surrogate.
* **Sparse package** (`ssx.msix`): contains only `AppxManifest.xml` and the logo assets; the
  real files stay in the install directory (the *external location*). The manifest sets
  `uap10:AllowExternalContent` so the package may point outside itself.
* **Registration** happens once per user at install time (see below).

### Why `com:SurrogateServer`

The manifest registers the DLL under `com:ComServer/com:SurrogateServer`, so Windows hosts it
out of process in `dllhost.exe`. A crash or hang in our code then cannot take down Explorer,
and the DLL is not loaded into every process that opens a file dialog. (`panic = "abort"` in
the workspace release profile is acceptable here for the same reason: it kills `dllhost`, not
Explorer.)

## The manifest

Generated by `sparse_package_manifest(&SparsePackageParams::ssx_defaults("<a.b.c.d>"))`.
The parts that matter:

```xml
<Identity Name="Ssx.ShellExtension" Publisher="CN=ssx" Version="0.1.0.0" ProcessorArchitecture="x64" />
<Properties> ... <uap10:AllowExternalContent>true</uap10:AllowExternalContent> </Properties>
<Applications>
  <Application Id="Ssx" Executable="ssx.exe" uap10:TrustLevel="mediumIL" uap10:RuntimeBehavior="win32App">
    <Extensions>
      <desktop4:Extension Category="windows.fileExplorerContextMenus">
        <desktop4:FileExplorerContextMenus>
          <desktop5:ItemType Type="*">
            <desktop5:Verb Id="SsxUpload" Clsid="{...}" />
          </desktop5:ItemType>
          <desktop5:ItemType Type=".png"> <desktop5:Verb Id="SsxEdit" Clsid="{...}" /> ...
          <desktop5:ItemType Type="Directory"> <desktop5:Verb Id="SsxUpload" .../>
        </desktop4:FileExplorerContextMenus>
      </desktop4:Extension>
      <com:Extension Category="windows.comServer">
        <com:ComServer>
          <com:SurrogateServer DisplayName="ssx context menu">
            <com:Class Id="..." Path="ssx_shell_ext.dll" ThreadingModel="STA" />
```

* `ItemType Type` is `*`, `Directory`, or a dotted extension. The generator maps
  `FilterKind::Any` to `*`, image/video/custom filters to their extensions, and adds
  `Directory` when the filter accepts folders. The same verb id appears under several item
  types.
* **CLSIDs** are derived from the action id (`guid_for("ssx-shell:explorer-command:<id>")`),
  so they are identical across builds; changing one orphans the previous registration.
  `Verb/@Id` (`SsxUpload`, `SsxEdit`, `SsxUploadVideo`) must be unique per package.
* `com:Class/@Path` is resolved against the package root, which for a sparse package is the
  external location; to be confirmed on a real system (the DLL must sit next to `ssx.exe`).
* Minimum OS: `10.0.22000.0` (Windows 11). Windows 10 keeps using the classic verbs.
* `runFullTrust` is required because the surrogate launches/talks to a full-trust process.

## Signing requirements

The sparse package **must be signed**, and `Identity/@Publisher` must equal the certificate
subject exactly.

| Scenario | What to do |
|---|---|
| Development | Self-signed code-signing cert; import it into *Trusted People* (one-time, admin). Or enable Developer Mode and register the loose manifest: `Add-AppxPackage -Register AppxManifest.xml -ExternalLocation <install dir>`. |
| Release | Sign `ssx.msix` with an OV/EV code-signing certificate or Azure Trusted Signing: `signtool sign /fd SHA256 /a /f cert.pfx /p ... ssx.msix`. The DLL and `ssx.exe` should be signed too (SmartScreen, AV). |
| Packaging | `makeappx pack /d <staging dir> /p ssx.msix /nv` (`/nv` skips content validation because the executable is not inside the package). |
| Registration (per user, at install) | `Add-AppxPackage -Path ssx.msix -ExternalLocation "C:\Program Files\ssx"`, or from the installer `PackageManager.AddPackageByUriAsync` with `ExternalLocationUri`. |
| Removal | `Remove-AppxPackage` (package full name from `Get-AppxPackage Ssx.ShellExtension`). |

A missing or untrusted signature makes registration fail with `0x800B0100`/`0x80073CFF`;
the installer must then fall back to classic verbs and tell the user.

## `IExplorerCommand` contract per action

| Method | Behaviour |
|---|---|
| `GetTitle` | The action label (`Upload with ssx`). |
| `GetIcon` | `"<install dir>\ssx.exe,0"`. |
| `GetToolTip` | The action description. |
| `GetCanonicalName` | `GUID_NULL`. |
| `GetState` | `ECS_ENABLED` if every selected item matches the action's filter (and, for single-file actions, exactly one item is selected); otherwise `ECS_HIDDEN`. Cheap: extension check on `SIGDN_FILESYSPATH`; no I/O. Must not block. |
| `GetFlags` | `ECF_DEFAULT`. |
| `EnumSubCommands` | `E_NOTIMPL` (flat entries; a future "ssx" submenu would implement `IEnumExplorerCommand`). |
| `Invoke(IShellItemArray)` | Collect all paths (`GetCount`/`GetItemAt`/`GetDisplayName(SIGDN_FILESYSPATH)`; skip items without a file system path, e.g. virtual folders), then forward once (below). Return promptly. |

`GetState` and `Invoke` see the **whole selection in one call**, which is why this route has
none of the classic-verb limits (15/100 items, one process per file, 32 767-character command
line).

## Forwarding over `ssx-ipc`

`Invoke` sends one line and returns:

```json
{"cmd":"post-file","paths":["C:\\a b\\x.png","..."],"coalesce":false}
```

(The schema belongs to `ssx-core`; `action.exec_args[0]` maps to `cmd`.) The DLL uses
`ssx_ipc::Client::for_app("ssx")` and `send_or_spawn`, with the spawn closure starting
`<install dir>\ssx.exe` detached. The client derives the pipe name from the per-user runtime
directory, so the DLL and the app agree without configuration. The pipe is owner-only and
rejects remote clients, and the surrogate runs as the user, so no privilege boundary is crossed.

Open item for `ssx-ipc`: expose the endpoint name/`Location` publicly if the DLL wants to avoid
linking `interprocess`, or keep linking `ssx-ipc` (small: `interprocess`, `fs4`).

## Coexistence and install order

1. Always install the classic verbs (works everywhere, no signing).
2. On Windows 11 (build >= 22000) with a valid signature, additionally register the sparse
   package. Users then see the top-level entries; the classic ones remain under
   **Show more options**. If duplicates are undesirable, the installer can skip the classic
   verbs once the package registers successfully (they are independent and reversible).
3. Uninstall removes both.

## Test plan (when implemented)

* Keep the pure parts pure and unit-tested: filter-to-`GetState` decision, path collection
  given fake `IShellItem`s, JSON building with hostile paths.
* Golden manifest (exists) plus `makeappx` validation on a Windows CI runner.
* Manual matrix on Windows 11 22H2/23H2/24H2: single file, 200 files, folder, mixed
  selection, network path, OneDrive placeholder, non-ASCII/very long paths, app not running,
  app running elevated (pipe owner mismatch: expected to fail with a clear message).

## Known unknowns to verify on a real machine

* Path resolution of `com:Class/@Path` for sparse packages (relative to the external location).
* Exact registration error codes and the Developer Mode path.
* Whether `desktop5:ItemType` accepts our extension list sizes (dozens of item types).
